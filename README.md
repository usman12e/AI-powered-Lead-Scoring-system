# AI-Powered Lead Scoring System

A machine learning web application that predicts the probability of a sales lead converting into a paying customer. Built using a Multi-Layer Perceptron (MLP) neural network, a five-step preprocessing pipeline, and a Flask web interface.

**Course:** Artificial Intelligence Lab — Final Project  
**Dataset:** X Education Lead Scoring (Kaggle) — 9,240 rows  
**Model:** MLP Neural Network — Architecture (16, 8)  
**Evaluation:** 5-run mean ± standard deviation

---

## 1. Project Overview

A **lead** is a potential customer who has shown interest in a product — by visiting a website, filling out a form, or engaging with marketing material. A **lead scoring system** ranks those leads by their likelihood of converting into actual paying customers, so a sales team can focus their effort on the most promising ones.

This system takes six pieces of information about a lead, processes them through a trained neural network, and returns a conversion probability score between 0% and 100%, along with a label (Very Low / Low / Medium / High Potential).

The problem is framed as **binary classification**:

- **Input:** behavioral and demographic features about a lead
- **Output:** probability that `Converted = 1` (will buy)

## 5. Dataset

**Source:** Kaggle — X Education Lead Scoring Dataset  
**Size:** 9,240 rows, 37 original columns  
**Target column:** `Converted` (1 = became a paying customer, 0 = did not convert)  
**Overall conversion rate:** ~38.5%

X Education is an online course company. The dataset contains historical records of leads — people who visited their website, filled out a form, or interacted with their marketing — along with whether each lead eventually enrolled in a course.

We use 6 of the 37 original columns. The rest were excluded because they are either ID columns with no predictive value, post-conversion records that constitute a data leak (explained in Section 7), or columns with excessive missing data or near-zero variance.

## 6. Preprocessing Pipeline

Preprocessing runs in five sequential steps, each printed clearly to the terminal when `train.py` is executed. The pipeline is implemented in `preprocess.py` and follows the standard Raw Data → Cleaning → Transformation → Feature Engineering → Splitting flow.

### Step 1 — Cleaning

Raw data always contains errors. This step fixes all of them before any model sees the data.

| Issue | What It Means | Fix Applied |
|---|---|---|
| Wrong formats | Text like `"N/A"` or `"?"` in a numeric column | `pd.to_numeric(errors='coerce')` converts to `NaN` |
| Impossible values | Negative visit counts or negative time | Set to `NaN` — physically impossible |
| Outliers | Extreme values distorting learning | Capped at Q3 + 3×IQR (Winsorisation) |
| Inconsistent labels | `"google"` vs `"Google"` vs `" Google "` | `.str.strip().str.title()` |
| Missing values | `NaN` cells the model cannot process | Numerical → median; Categorical → mode |
| Duplicates | Identical rows counted twice | `drop_duplicates()` |

**Why median and not mean for missing numerical values?**
Mean is pulled by outliers. If 9 leads visited 3 times and one visited 500 times, the mean is 52 — a value no actual lead has. The median is 3, which represents the typical lead accurately.

**Why cap outliers instead of deleting them?**
Deleting an outlier removes all other information in that row. Capping limits only the extreme number while keeping the lead's source, occupation, and activity intact.

### Step 2 — Transformation

**Label Encoding** converts text categories to integers. The MLP performs matrix multiplications and cannot process the string `"Google"`. `LabelEncoder` assigns each unique value a stable integer. The encoder is saved to disk so Flask applies the exact same mapping at prediction time.

**Standard Scaling** transforms every feature to mean = 0, standard deviation = 1. Without scaling, `Total Time Spent on Website` (range 0–4,000) produces massive gradient updates while `TotalVisits` (range 0–30) produces tiny ones. The model would learn almost entirely from time spent and ignore everything else. After scaling, every feature contributes equally.

**Why StandardScaler over MinMaxScaler?**
MinMaxScaler compresses everything to [0, 1], but one extreme outlier forces all other values to cluster near zero. StandardScaler is computed from mean and standard deviation — both derived from the bulk of the data — and is not distorted by extremes.

### Step 3 — Feature Engineering

Two new features are derived that capture interaction effects the model cannot discover on its own. See Section 8 for full details.

### Step 4 — Splitting

80% training, 20% test. `stratify=y` ensures both halves contain the same ~38.5% conversion rate. `random_state=42` makes the split reproducible on every run.

## 7. Feature Selection and the Data Leak

We use **6 features**, not all 37 available columns. The rule is: only include features that a sales representative can realistically know about a lead *before* the conversion happens. Features recorded *after* conversion are consequences, not predictors.

### The Data Leak: "Receive More Updates About Our Courses"

This column was initially included. The model's predictions immediately jumped to ~100% whenever "Yes" was selected. Investigation revealed:

```
Value    Count    Converted    Conversion Rate
Yes      1,780    1,780        100.0%
No       7,460    1,781         23.9%
```

Every single "Yes" row is a converter. Zero exceptions across 1,780 rows. This is a **data leak** — the column was recorded *after* conversion. Existing customers were asked if they wanted updates and said yes. It does not predict conversion; it records conversion after the fact.

Training on a leaked column is equivalent to giving the model the answer sheet. The model assigns nearly all its weight to this one column, making every other feature irrelevant. The column was removed from all files: `preprocess.py`, `app.py`, and `index.html`.

### Final 6 Features

| Feature | Type | Why Included |
|---|---|---|
| `TotalVisits` | Numerical | Return frequency — strongest engagement signal |
| `Total Time Spent on Website` | Numerical | Strongest single predictor (58pp spread across quartiles) |
| `Page Views Per Visit` | Numerical | Depth of engagement per session |
| `Lead Source` | Categorical | Referrals convert at 71%; Google at 28% — 43pp difference |
| `Last Activity` | Categorical | Phone calls convert at 77%; SMS at 25% — 52pp difference |
| `What is your current occupation` | Categorical | Professionals convert at 57%; students at 24% |

## 8. Feature Engineering

Two additional features are derived from the original six, capturing interaction effects the model cannot learn by treating columns independently.

### Engagement Score = TotalVisits × Total Time Spent on Website

A lead who visits 10 times for 30 minutes each is fundamentally different from one who visits 10 times for 30 seconds each. Both have 10 visits. The raw columns processed separately miss this distinction. The product creates an explicit compound signal — a lead with Engagement Score 300 is genuinely more interested than one with score 5, even if they have the same visit count.

The MLP can only compute linear combinations of its inputs within a layer. It cannot discover a multiplicative relationship between two columns on its own. Making the product explicit gives the model information it otherwise could not access.

### Pages-per-Minute Ratio = Page Views Per Visit ÷ (Total Time Spent + 1)

This distinguishes two very different browsing behaviours. A high ratio (many pages, little time) indicates skimming — clicking around without genuine interest. A low ratio (few pages, long time) indicates careful reading — deep engagement with the content. The `+ 1` prevents division by zero for leads with zero recorded time.

### Why `eng_params.pkl` Is Required

Both engineered features are standardised using the mean and standard deviation computed across all 9,000+ training rows. At prediction time, Flask receives one single lead. Computing mean and std from one value would always return mean = that value and std = 0 — producing a constant output of 0 regardless of the input. `eng_params.pkl` stores the four training-time statistics so the transformation is identical between training and prediction.

### Final Feature Matrix (8 total)

```
[0] TotalVisits                     — original, scaled
[1] Total Time Spent on Website     — original, scaled
[2] Page Views Per Visit            — original, scaled
[3] Lead Source                     — original, encoded + scaled
[4] Last Activity                   — original, encoded + scaled
[5] What is your current occupation — original, encoded + scaled
[6] Engagement Score                — engineered, standardised via eng_params.pkl
[7] Pages-per-Minute Ratio          — engineered, standardised via eng_params.pkl
```

## 9. Model Selection

Four algorithms were evaluated. MLP was chosen based on empirical F1-score comparison across 5 runs.

### Why Not Naive Bayes?

Naive Bayes assumes every feature is statistically independent of every other. It assumes that knowing how much time someone spent on the site tells you nothing about how many pages they viewed. This is false — these features are strongly correlated. Naive Bayes ignores all such relationships, fundamentally misrepresenting the data structure. `GaussianNB` additionally assumes each feature follows a bell-curve distribution, which many of our skewed features do not.

### Why Not KNN?

KNN stores the entire training set and, at prediction time, searches for the k most similar leads to vote on the outcome. This is slow on 7,000+ training rows. More critically, KNN suffers from the curse of dimensionality — in 8-dimensional space, the distances between all points become nearly equal, so "nearest neighbour" loses its meaning. KNN also cannot output a natural probability, only discrete class labels.

### Why Not a Single Perceptron?

A perceptron draws a single flat hyperplane through the feature space. Lead conversion is not linearly separable — there is no flat boundary that correctly divides all converters from all non-converters. The decision boundary is simply too rigid for this problem.

### Why MLP?

- Learns non-linear decision boundaries through hidden layers with ReLU activations
- Learns feature interactions — first layer learns combinations, second layer learns patterns of combinations
- Outputs genuine probabilities via `predict_proba()`, directly usable as a 0–100% score
- Handles the mix of numerical and encoded categorical features well after scaling

## 10. MLP Architecture Justification

**Architecture:** Input(8) → Hidden Layer 1(16 neurons) → Hidden Layer 2(8 neurons) → Output(1)

### Why Two Hidden Layers?

Layer 1 learns constructs: "highly engaged lead", "passive browser". Layer 2 learns patterns among those constructs: "highly engaged professional = strong buying signal". One layer cannot produce this second level of abstraction.

### Why 16 Neurons in the First Layer?

Two standard heuristics both suggest 16:
- **Double the inputs:** 2 × 8 = 16
- **Two-thirds rule:** ⅔ × (inputs + outputs) ≈ 6, scaled up = ~16

Five architectures were empirically tested (8), (16), (16,8), (32,16), (32,16,8) and compared by F1-score. `(16, 8)` produced the best result. Three layers overfit on 9,000 rows; the larger two-layer architecture added minimal gain at higher cost.

### Why ReLU Activation?

Sigmoid and tanh saturate — for extreme inputs their output is flat and their derivative approaches zero. During backpropagation, multiplying near-zero gradients through every layer means the gradient reaching early layers is negligibly small. Early layers stop learning. This is the vanishing gradient problem. ReLU's derivative is exactly 1 for positive inputs — gradients flow cleanly, training is fast and stable.

### Why Adam Optimizer?

Adam maintains a separate adaptive learning rate for each weight, adjusted based on recent gradient history. SGD applies one fixed rate to all weights. Some weights need large updates early in training; others need fine-grained tuning. Adam handles both automatically, converging faster and more reliably.

## 11. Evaluation Strategy — 5 Runs with Mean ± Std

A single train/test split can be misleading. A lucky partition produces inflated metrics; an unlucky one depresses them. One number tells you nothing about the model's consistent performance.

### Protocol

The model is trained and evaluated five times using split seeds 0, 1, 2, 3, 4. Each seed produces a genuinely different 80/20 partition of the full dataset. All four metrics are recorded per run. Mean and standard deviation are computed across the five runs.

- **Mean** — the true average performance across different data conditions
- **Standard deviation** — how stable and reliable the model is

A small std means the model performs consistently regardless of which specific rows happen to end up in the test set. A large std would indicate the model is brittle.

### Final Model

After the 5-run evaluation, a final model is trained on a fixed split (`random_state=42`) and saved as `model.pkl`. The fixed seed ensures complete reproducibility — the exact same model is produced on every run of `train.py`.

## 12. Evaluation Metrics Explained

**Accuracy** — percentage of all predictions that were correct. Can be misleading with imbalanced data — predicting "will not convert" for every lead achieves 61.5% accuracy without learning anything useful.

**Precision** — of all leads predicted to convert, what fraction actually did? Low precision wastes the sales team's time on leads who will not buy.

**Recall** — of all leads who actually converted, what fraction did the model catch? Low recall means real buyers are missed and left uncontacted.

**F1-Score** — `2 × (Precision × Recall) / (Precision + Recall)`. Only high when both precision and recall are high simultaneously. The most honest single metric for imbalanced datasets.

**Confusion Matrix** — breaks predictions into four categories: True Positives (correctly caught buyers), True Negatives (correctly identified non-buyers), False Positives (wasted sales calls), and False Negatives (missed real buyers — the most costly error in a sales context).

**ROC Curve / AUC** — plots True Positive Rate vs False Positive Rate at every threshold. AUC = 0.5 means the model is no better than random. AUC = 1.0 is a perfect model. AUC measures the model's ability to rank leads correctly — a lead scored at 80% should be genuinely more likely to convert than one scored at 40%.

## 13. Flask Backend

Flask is a minimal Python web framework. The entire backend is `app.py`.

**Why Flask and not Django?** Django is designed for large applications with databases, authentication systems, and admin interfaces. For a single-page prediction application with one route, Django's overhead is unnecessary. Flask keeps the server code minimal and readable.

**Why load model files at startup, not inside the route?**

```python
# Correct — loads once at startup
model = joblib.load('models/model.pkl')

# Wrong — would load on every single prediction request
def predict():
    model = joblib.load('models/model.pkl')
```

File loading takes ~100ms per call. Thousands of predictions would each pay this cost unnecessarily. Loading once at startup means every request is served from memory.

**The prediction pipeline in `app.py`** replicates every preprocessing step from `preprocess.py` on the single new input: encode categoricals with the saved encoders, scale with the saved scaler, compute and standardise both engineered features using saved params, stack into an 8-element array in the exact same column order as `FEATURES`, call `predict_proba()`, return the result as JSON.

**Why Fetch API instead of a regular form submit?** A regular HTML form submit reloads the entire page. The Fetch API sends data in the background and updates only the result section, enabling the animated score ring and counting number to play without interruption.

## 15. Design Decisions Summary

| Decision | Choice Made | Alternative Rejected | Reason |
|---|---|---|---|
| Algorithm | MLP (16, 8) | Naive Bayes, KNN, Perceptron | MLP handles non-linearity, learns feature interactions, outputs probabilities |
| Activation | ReLU | Sigmoid, Tanh | Avoids vanishing gradient — early layers keep learning throughout training |
| Optimizer | Adam | SGD | Adaptive per-weight learning rates; converges faster on this dataset size |
| Missing value fill | Median / Mode | Mean / Deletion | Median is robust to outliers; deletion removes valid data rows |
| Outlier handling | Winsorisation (cap) | Deletion | Keeps the row; only limits the extreme numeric value |
| Scaling | StandardScaler | MinMaxScaler | Not distorted by outliers; works correctly with the preprocessing order used |
| "Receive Updates" column | Removed | Kept as feature | 100% of "Yes" rows are converters — a data leak, not a genuine predictor |
| Feature count | 6 original + 2 engineered = 8 | All 37 columns | Training and prediction use exactly the same features — no shape mismatch possible |
| Evaluation | 5 runs, mean ± std | Single run | One split is not statistically meaningful; multiple runs reveal true average performance and stability |
| Backend framework | Flask | Django | Flask is appropriate for a single prediction endpoint; Django overhead is unnecessary |
| Form submission | Fetch API | HTML form submit | No page reload; enables smooth score animation |
